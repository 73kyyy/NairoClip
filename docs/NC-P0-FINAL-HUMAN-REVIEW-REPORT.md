## 2. 256 个调用点兼容性审查

### 2.1 五个辅助函数的签名与语义

| 函数 | 签名（修复前 = 修复后） | 语义变化 |
|---|---|---|
| `JNum` | `double JNum(const std::string&, const std::string&, double def)` | 仅**定位方式**变；数值仍 `strtod` |
| `JInt` | `int64_t JInt(const std::string&, const std::string&, int64_t def)` | **无**（仍经 `JNum`→double） |
| `JStrField` | `std::string JStrField(const std::string&, const std::string&)` | 仅定位方式 + 转义解码更完整 |
| `JVecDouble` | `bool JVecDouble(const std::string&, const std::string&, std::vector<double>*)` | 仅定位方式变；逐元素仍 `strtod` |
| `JVecU64` | `bool JVecU64(const std::string&, const std::string&, std::vector<uint64_t>*)` | 仅定位方式变；逐元素仍 `strtoull` |

**签名零变化 → 256 个调用点（`nc_jni.cpp` 内 62+148+32+7+7 次出现）无需改动，实际也未改动**
（`git diff` 中 `nc_jni.cpp` 仅 +32/−69，全部位于辅助函数区）。

### 2.2 「根对象直接成员」约定是否被所有调用点满足

**关键证据 —— 前端 args 的构造方式保证顶层扁平**：

`mobile/assets/engine.js:91-96`（编辑主通道）：

```js
edit(payload) {
  const op = payload && payload.op;
  const args = Object.assign({}, payload);   // ← 浅拷贝：args 顶层键 == payload 顶层键
  delete args.op;
  const r = parseBridge(this.bridge.call(op, JSON.stringify(args)));
}
```

`mobile/assets/nc-api.js:33-41`（348 个 `NC_API.*` 方法统一入口）：

```js
function call(fn, args) {
  raw = b.call(fn, JSON.stringify(args || {}));   // ← 调用方传入的对象原样透传
}
```

结论：**所有参数对象都是"一层扁平对象"**。嵌套结构只能作为某个**值**出现
（数组如 `material_ids`，或 JSON 字符串如 `result_payload`），
而 JNI 读取的是**顶层键** → 与新实现"只匹配根对象直接成员"完全一致。

**旁证**：`nc_apply_command` 走独立 JNI 方法 `nativeApplyCommand`
（`nc_jni.cpp:1954-1959`），把整个 JSON 字符串直接交给 C ABI，
**不经过 `FindKey`** → 不受本次改动影响。

### 2.3 是否存在依赖"嵌套键搜索"的历史调用

| 检查 | 结果 |
|---|---|
| JNI 读取的 **115** 个不同键名，是否为根级标量 | ✅ 全部为标量键（对象/数组仅作值传递） |

| 实测：旧实现能读嵌套键（副作用），新实现读不到 | 是 —— 见下表 |

| 载荷 | 键 | 修复前 | 修复后 | 判定 |

## 3. 重复键安全性审查

### 3.1 实测结果

| ID | 输入 | 键 | 状态 | 实际取值 |
|---|---|---|---|---|
| D1 | `{"track_index":2,"track_index":1}` | track_index | **DuplicateKey** | 回落默认 **0** |
| D2 | `{"a":{"track_index":9,"track_index":8},"track_index":2}` | track_index | Ok | **2**（嵌套重复不影响根） |
| D3 | `{"a":1,"a":2,"track_index":2}` | track_index | Ok | **2**（非目标键重复被忽略） |
| D4 | `{"track_index":0,"track_index":0}` | track_index | **DuplicateKey** | 回落默认 **0** |
| D5 | `{"name":"a","name":"b"}` | name | **DuplicateKey** | 回落 `""` |

### 3.2 三项审查结论

| 审查点 | 结论 |
|---|---|
| 能否识别根对象直接成员中的重复键 | ✅ 能（D1/D4/D5），且**值相同也判重复**（D4，策略一致） |
| 嵌套对象内部同名键是否影响根解析 | ✅ **不影响**（D2 正确读到根值 2）；嵌套内部重复不检测（按设计只校验目标键） |
| 重复键是否导致危险默认值回退 | ⚠️ **是，存在风险**（见 3.3） |

### 3.3 风险：重复键 → 默认值 → 静默错误操作

**实测**：`{"track_index":2,"track_index":1}` → `JInt` 返回默认 `0`
→ 若该参数用于定位轨道，**会静默操作轨道 0**，与 R2 的严重性同级。

| 风险面 | 评估 |
|---|---|
| 触发可能性 | **极低** —— `JSON.stringify` 不可能产生重复键；需人工构造 |
| 触发后后果 | **高** —— 无错误提示，作用于错误轨道/错误参数 |
| 与修复前对比 | 修复前取第一个（2），修复后取默认（0）。**两者都是"错"，但表现不同** |

### 3.4 最小修复方案（仅提出，本轮不实施）

| 方案 | 改动量 | 评价 |
|---|---|---|
| **A（推荐）**：在 `nc_jni.cpp` 的 `DispatchEdit` 入口加一次「目标键重复检测」，命中则返回 `Err("参数重复键")` | 约 10 行，不改 256 个调用点 | 把静默变显式失败，符合"不静默错误"原则 |
| B：`findJsonMember` 遇 `DuplicateKey` 直接判 `Malformed` | 1 行 | 效果同 A 的取值（仍回落默认），**无法变成显式错误** |
| C：维持现状 + 文档声明"重复键视为未提供" | 0 行 | 仍是静默回退，不推荐 |

> **建议**：采用 A，但**需单独授权**（属新增行为，超出本 P0 修复的既定范围）。

### 4.1 接受 / 拒绝清单

| 输入类别 | 处置 |
|---|---|
| `\uXXXX` 基本平面 | ✅ 接受 |
| 合法代理对（高+低） | ✅ 接受，正确合成 4 字节 |
| 原始 UTF-8（中文/emoji） | ✅ 接受，原样透传 |
| 不完整 `\u` | ✅ 拒绝（`Malformed`） |
| 非十六进制 `\uZZZZ` | ✅ 拒绝（`Malformed`） |
| 非法转义 `\x` | ✅ 拒绝（`Malformed`） |
| **孤立高/低代理** | ⚠️ **当前接受并产出非法 UTF-8** |
| **`\u0000`** | ⚠️ **当前接受并产出内嵌 NUL** |

### 4.2 两项新发现（本审查新增，非既有问题）

| ID | 问题 | 影响 | 最小修复方案 |
|---|---|---|---|
| **R-1** | 孤立代理（`\ud83c` / `\udfac`）被接受，输出 `ED A0 BC` / `ED BE AC`（UTF-8 中代理码点非法） | 若该字符串传给 `nc_*` 并落盘/显示，产生非法 UTF-8；可能导致下游校验失败或界面乱码 | 在 `parseString` 的 `\u` 分支：若码点落在 `D800–DFFF` 且**未**配对成合法代理对 → `return fail("孤立代理项")`。约 3 行 |
| **R-2** | `\u0000` 被接受，`std::string` 含内嵌 NUL；`JStrField` 返回后经 `.c_str()` 传给 C ABI 会**在 NUL 处截断** | 名称/路径被静默截短 | 在 `\u` 分支拒绝 `cp == 0`（或转为 U+FFFD）。约 2 行 |

> 两项均为**新代码的健壮性缺口**，不构成对旧行为的回归
> （旧实现对这两类输入返回字面 `u d83c` / `u0000`，同样不正确）。
> **本轮不实施**，仅提出；是否纳入需人工决定。

## 5. JNI 生命周期审查

### 5.1 全部获取/释放点

| 位置 | 代码 | 配对情况 |
|---|---|---|
| `nc_jni.cpp:44-47` `JStr()` | `GetStringUTFChars` → 空指针检查 → `std::string out(utf)` → `ReleaseStringUTFChars` | ✅ 成对，**Get 与 Release 之间无 early return** |
| `nc_jni.cpp:2656-2660` 崩溃处理器安装 | `GetStringUTFChars` → `installCrashHandler` → `if (cdir != nullptr) Release` | ✅ 成对，Release 有判空且必经 |
| `nc_jni.cpp:52` `ToJStr()` | `NewStringUTF(s.c_str())` | 无 Get，无需 Release |
| `nc_jni.cpp:2426-2430` 文本渲染 | 5 次 `NewStringUTF` | 无 Get，无需 Release |

**统计**：`GetStringUTFChars` 2 处 / `ReleaseStringUTFChars` 2 处 → **完全配对**。
`JStr()` 是 40 个调用点的唯一通用入口，因此全部入参字符串走同一条配对路径。

### 5.2 异常路径

| 场景 | 行为 |
|---|---|
| `jstring == nullptr` | `JStr` 立即返回 `{}`，未获取任何资源 ✅ |
| `GetStringUTFChars` 返回 `nullptr`（OOM/异常） | 立即返回 `{}`，**未 Release 是对的**（未获取） ✅ |
| `std::string out(utf)` 抛 `bad_alloc` | ⚠️ 理论上 `ReleaseStringUTFChars` 不会执行 → 泄漏。**与修复前同形**，属既有风险（P3） |
| `NewStringUTF` 返回 `nullptr` | 返回 null jstring，无资源泄漏；Java 侧收到 null（无错误处理，既有行为） |

### 5.3 空字符串 / 连续调用

| 项 | 审查结论 |
|---|---|
| 空字符串 `jstring ""` | `GetStringUTFChars` 返回 `""`，`std::string` 为空 → 返回 `""` ✅ |
| 连续调用 | 每次调用独立 Get/Release，无跨调用状态 → 无累积泄漏（**理论**，需真机确认） |
